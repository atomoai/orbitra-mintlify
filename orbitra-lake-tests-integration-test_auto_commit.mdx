# `orbitra.lake.tests.integration.test_auto_commit`

## Classes

### `TestAutoCommitIntegration`


Pins Unity Catalog's one-snapshot-per-commit rule and the SDK's answers to it, end-to-end.

Unity Catalog rejects transactions carrying more than one snapshot with `CommitFailedException:
Adding multiple snapshots in a single update is not supported` — the reason
`PyIcebergDB._set_transaction_auto_commit` exists. The overwrite paths no longer depend on the
workaround: `overwrite_partitions_data` (ORBITRA-835), `overwrite_data_by_custom_columns` (ORBITRA-833)
and the unpartitioned `overwrite_data` commit a single atomic overwrite snapshot.


**Methods:**

#### `test_concurrent_append_does_not_survive_unpartitioned_overwrite`

```python
test_concurrent_append_does_not_survive_unpartitioned_overwrite(self, monkeypatch)
```

With write.delete.isolation-level=snapshot, an append that lands mid-overwrite is still a conflict.

The overwrite validates under write.update.isolation-level (serializable here): the append fails its
validation, the orbitra @retry redoes the overwrite, and only the rows of the overwrite remain.


#### `test_concurrent_unpartitioned_overwrite_keeps_one_writer`

```python
test_concurrent_unpartitioned_overwrite_keeps_one_writer(self, monkeypatch)
```

Two overwrites of an unpartitioned table never end with the rows of both.

Just before this writer commits its rows, a competing writer overwrites the whole table, so Unity answers
this commit with a real 409. Its overwrite fails pyiceberg's validation and the orbitra @retry redoes it.


#### `test_overwrite_by_custom_columns_is_single_snapshot`

```python
test_overwrite_by_custom_columns_is_single_snapshot(self)
```

Custom-columns overwrite commits exactly one snapshot, even with the auto-commit workaround disabled.
