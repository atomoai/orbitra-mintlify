#### `test_parallel_overwrite_data`

```python
test_parallel_overwrite_data(self, monkeypatch, caplog)
```

Concurrent overwrite_data calls on distinct partitions all succeed without orbitra's @retry firing.

Iceberg's optimistic concurrency operates at the table-snapshot level, so parallel commits to
disjoint partitions still race on the catalog's snapshot pointer and raise CommitFailedException.
Since pyiceberg 0.12 ``Transaction.commit_transaction`` retries that failure itself: it refreshes
the table, validates the concurrent snapshots against the overwrite's conflict predicate (the
touched partitions) and re-plans the snapshot. Orbitra's @retry decorator on the overwrite_*
methods is therefore only a last resort for same-partition conflicts (ValidationException) and
must stay idle here. This test verifies three things: every worker returns successfully, the
conflict was actually resolved inside pyiceberg (its retry warning was logged), and orbitra's
own @retry path never slept.

The patch targets ``orbitra.lake.utils.retry.sleep`` specifically (the name bound by
``from time import sleep`` in that module), not the global ``time.sleep``, so the counter reflects
orbitra's retry alone.

### `TestAtomicPartitionOverwrite`


Partition overwrite must land as a single atomic overwrite snapshot (ORBITRA-835).

The upstream ``dynamic_partition_overwrite`` commits a delete snapshot and an append snapshot
separately (Unity Catalog rejects multi-snapshot transactions), leaving a visible intermediate
state between them. These tests pin the replacement semantics: one commit per operation, with
the same partition-replacement contract as before.

```python
test_concurrent_writer_on_untouched_combination_of_composite_spec_is_not_a_conflict(self, monkeypatch, caplog)
```

A concurrent append to (a,2) while (a,1) and (b,2) are overwritten is resolved inside pyiceberg, without orbitra's @retry.

The conflict-detection predicate must stay exact. If it claimed the cross product of the touched values,
(a,2) would be flagged as a conflict, raise ValidationException and cost the ~45s of retry backoff.

#### `test_metadata_only_discovery_prunes_manifests_of_untouched_partitions`

```python
test_metadata_only_discovery_prunes_manifests_of_untouched_partitions(self, monkeypatch)
```

Manifest pruning uses the exact partition predicate, not the conservative scan filter.

`In` only prunes a manifest when every touched value falls outside its partition summary range
(`_ManifestEvalVisitor.visit_in`), so a sparse set over a composite spec leaves nearly every manifest
unpruned and fetches its entries from storage for nothing. The exact Or of per-partition Ands prunes by
value, and the manifest evaluator runs once per manifest — not once per file — so the conservative shape
that scan planning needs buys nothing here.

#### `test_overwrite_refuses_full_table_replacement_after_partition_field_removed`

```python
test_overwrite_refuses_full_table_replacement_after_partition_field_removed(self)
```

Removing the partition field must not silently widen an overwrite into a full-table replacement.

overwrite_data picks partition replacement or full-table replacement from the table's *current*
partition metadata. Once an external engine drops the partition field, the very same call that used to
replace one partition replaces the whole table, and the untouched partitions are deleted with no error.
The destructive transition is cheap to spot before anything is written — the current spec has no fields
while the spec history does — and it is distinct from a table that merely accumulated specs (a
Databricks OPTIMIZE leaves the partitioned spec as the default, and that overwrite stays correct).


#### `test_overwrite_refuses_when_compound_spec_loses_a_field`

```python
test_overwrite_refuses_when_compound_spec_loses_a_field(self)
```

Dropping one field of a compound spec must not silently coarsen the replacement scope.

Routing still picks partition replacement, so a guard that only looks for a fully unpartitioned table
never sees this one, yet replacing (a, 1) now replaces every row with p1='a'. The response reports
`modified_partitions=[('a',)]`, which is accurate under the new spec and misleading for a caller who
still thinks in (p1, p2). Both dangerous shapes share one signal: the set of partition source columns
shrank — the fully unpartitioned table is just its degenerate case.

#### `test_same_partition_conflict_is_replanned_by_orbitra_retry`

```python
test_same_partition_conflict_is_replanned_by_orbitra_retry(self, monkeypatch, caplog)
```

A concurrent writer replacing the SAME partition is resolved by orbitra's @retry, not by pyiceberg.

pyiceberg (>= 0.12) retries a CommitFailedException internally, but it keeps the planned file set
frozen and validates it against the refreshed table: files it wanted to delete were already
deleted by the competing writer, so it raises ValidationException instead of re-planning. The
orbitra decorator catches that and re-executes the whole operation from a fresh snapshot, so the
last writer wins and the table never holds both versions of the partition.
