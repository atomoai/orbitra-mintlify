# `orbitra.lake.tests.integration.test_predictive_optimization`

## Classes

### `TestPredictiveOptimizationIntegration`


Runs Databricks OPTIMIZE / VACUUM for real against SDK tables and pins that the SDK keeps working afterwards.

Databricks Predictive Optimization periodically runs OPTIMIZE and VACUUM on Unity Catalog tables. ORBITRA-908
showed that OPTIMIZE compacts a partitioned SDK table into a single file written under the unpartitioned spec,
and that in this state a partition overwrite silently became an append. The fix is covered by unit tests that
*simulate* that file layout (`_add_external_string_file`, `_create_table_evolved_from_unpartitioned` in
`orbitra/lake/tests/lake/test_data.py`); this class is the real proof, using Databricks as the adversary.

Table contents are pinned with pytest-snapshot (``snapshots/test_predictive_optimization/<test>/<step>.json``),
sorted by (country, id) so the files are deterministic and a duplicated row shows up as an extra record.

Every scenario owns its table, and every table is registered in ``TABLES_TO_CLEANUP`` so the class fixture
drops it even when a test fails halfway. Each remote call is timed and logged: OPTIMIZE on a cold SQL warehouse
takes tens of seconds, so the scenarios issue as few of them as possible.
